# コード解説

このコマンドは、指定されたファイルまたはコードブロックを、受講者にも分かりやすく解説します。

## 引数

`$ARGUMENTS` には解説対象のファイルパスまたは行番号範囲が入ります。

例:
- `/explain force-app/main/default/classes/LeadScoringService.cls`
- `/explain LeadController.cls:25-40`（特定の行範囲）
- `/explain`（現在開いているファイル）

## 実行手順

1. `$ARGUMENTS` から対象を特定
2. ファイル全体または指定範囲を読み込む
3. 関連するファイル（呼び出し元・呼び出し先）も必要に応じて参照

### Step 4: 解説のポイント

#### A. 「何をしているか」と「なぜそうするか」を分ける

```
[悪い例]
このコードは SOQL を実行しています。

[良い例]
このコードは Lead オブジェクトから情報を取得しています（何をしているか）。
なぜ SOQL を使うかというと、Salesforce のデータベースから情報を引き出す
唯一の方法だからです（なぜそうするか）。
```

#### B. アナロジー（たとえ話）を活用

```
[例: WITH SECURITY_ENFORCED]
これは「クエリの検問所」のようなものです。
ユーザーが見てはいけない項目を取得しようとすると、ここでブロックされます。
イメージとしては、図書館で会員カードを見せないと借りられない本があるのと同じです。
```

#### C. Java/JavaScript との対比

研修生は Java を学んでいるので、Java との対比で説明：

```
[例: トリガー]
Java では「イベントリスナー」を実装してオブジェクトの変更を検知しますが、
Apex の「トリガー」も同じような仕組みです。
Lead が作成・更新・削除されたタイミングで、トリガー内のコードが自動実行されます。
```

#### D. 視覚的な説明

可能なら ASCII アートや図で説明：

```
[例: ループ内 SOQL の問題]

❌ 悪い書き方（ループ内 SOQL）:
[Lead 100件] → for each [Lead] → SOQL 実行 → SOQL カウンタ +1
                                                ↓
                                          100回繰り返し
                                                ↓
                                     ガバナ制限 (100クエリ) 超過 ✗

✅ 良い書き方（ループ外 SOQL）:
[Lead 100件] → 1回の SOQL でまとめて取得 → SOQL カウンタ +1のみ
                                              ↓
                                  for each で処理（SOQL 実行なし）
                                              ↓
                                      ガバナ制限内 ✓
```

#### E. 段階的に深掘り

```
[第1層: ざっくり理解]
このメソッドはリードのスコアを計算します。

[第2層: 詳細]
属性スコア、行動スコア、興味スコアの 3 軸を合算し、
合計スコアからカテゴリ（Hot/Warm/Cold/Low）を判定します。

[第3層: 内部実装]
各 Scorer クラスがそれぞれ責任を持って計算し、
LeadScoringService が統括する設計になっています。
これは「責任分離の原則」と呼ばれる設計パターンです。
```

## 出力例

```markdown
# コード解説: LeadScoringService.cls

## このコードは何をするコードか

リードを 3 つの軸（属性・行動・興味）で評価して、合計スコアを計算するクラスです。

## 全体の流れ

1. リード ID を受け取る
2. 3 つの Scorer クラスを呼び出してそれぞれのスコアを計算
3. 合算して最終スコアを算出
4. カテゴリ（Hot/Warm/Cold/Low）を判定
5. Lead レコードを更新

## セクションごとの詳細解説

### セクション 1: メインメソッド

**コード**:
```apex
public static void calculateScores(Set<Id> leadIds) {
    if (leadIds == null || leadIds.isEmpty()) return;
    
    Map<Id, Lead> leadMap = new Map<Id, Lead>([
        SELECT Id, Industry, NumberOfEmployees, Title, LeadSource
        FROM Lead
        WHERE Id IN :leadIds
        WITH SECURITY_ENFORCED
    ]);
    ...
}
```

**何をしているか**:
複数のリードのスコアをまとめて計算します。
最初に必要な情報を一度に取得して、その後の処理で使い回します。

**なぜそう書くのか**:
Salesforce の「バルク化」パターンを実践しています。
複数のリードを一件ずつ処理すると、1件ごとに SOQL が実行され、
リードの数が増えるとガバナ制限に引っかかってしまいます。
ここでは Set<Id> を引数にして、一度の SOQL で全リードを取得しています。

**Salesforce 特有のポイント**:
- `Set<Id>`: 重複しない Id のコレクション
- `Map<Id, Lead>`: Id をキーにして Lead を引ける Map
- `WITH SECURITY_ENFORCED`: ユーザーに権限がない項目があるとエラーになるセキュリティ機能

**関連する概念**:
- バルク化: 複数件を一度に処理するパターン
- ガバナ制限: 1トランザクションあたりのリソース上限（SOQL は100回まで）
- WITH SECURITY_ENFORCED: 項目レベルセキュリティの自動適用

## 重要なポイント（受講者へのメッセージ）

1. **バルク化は Salesforce 開発の基本**: 必ず複数件処理を想定してコードを書く
2. **セキュリティは標準で組み込む**: WITH SECURITY_ENFORCED を癖にする
3. **責務分離**: 1 つのクラスに 1 つの責任。Scorer が 3 つに分かれている理由

## よくある間違い

1. **ループ内 SOQL**:
   - 間違い: `for (Lead l : leads) { ... = [SELECT ... WHERE Id = :l.Id]; }`
   - 正しい: 一度のクエリで全件取得 → Map で関連付け
   - 理由: SOQL は 100 回までしか実行できない
