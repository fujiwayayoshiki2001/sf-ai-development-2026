# リファクタリング提案

このコマンドは、指定されたファイルに対して具体的なリファクタリング提案を生成します。

## 引数

`$ARGUMENTS` にはリファクタ対象のファイルパスが入ります。
省略された場合は、最近変更されたファイルを対象にしてください。

例:
- `/refactor` → 最近変更されたファイル
- `/refactor force-app/main/default/classes/LeadController.cls` → 指定ファイル

## 実行手順

### Step 1: 対象ファイルの分析

1. `$ARGUMENTS` で指定されたファイルを読み込む
2. ファイルタイプを判別（Apex / LWC / Flow）
3. プロジェクトの CLAUDE.md を参照してコーディング規約を確認

### Step 2: リファクタリング項目の特定

以下の観点から、リファクタすべき箇所を特定してください。

#### Apex / Trigger の場合

1. **ガバナ制限対応**
   - ループ内 SOQL/DML → バルクパターンへ
   - 不要なクエリ → Map による最適化

2. **セキュリティ強化**
   - WITH SECURITY_ENFORCED の追加
   - CRUD/FLS チェックの追加
   - SOQL インジェクション対策

3. **エラーハンドリング**
   - try-catch の追加
   - AuraHandledException でのラップ
   - Savepoint の活用

4. **責務分離**
   - 長すぎるメソッドの分割
   - クラスの責務整理（Controller / Service / Scorer 等）

5. **定数化**
   - マジックナンバー → LeadConstants
   - 重み値 → カスタムメタデータ参照

6. **命名改善**
   - 意味不明な変数名のリネーム
   - メソッド名と動作の一致

7. **テスト容易性**
   - private メソッドへの @TestVisible 付与
   - 依存性の分離

#### LWC の場合

1. **エラーハンドリング**
   - @wire / imperative call の catch
   - ToastEvent でのエラー通知

2. **パフォーマンス**
   - 不要な再レンダリングの解消
   - getRecord / getFieldValue の活用

3. **アクセシビリティ**
   - aria-label の追加
   - キーボード操作対応

4. **コンポーネント分割**
   - 巨大コンポーネントの分割

### Step 3: リファクタの提案

各リファクタ項目について、以下の形式で提案してください。

```markdown
### [リファクタ N] <変更内容>

**カテゴリ**: <ガバナ制限 / セキュリティ / 設計 等>

**対象**: `<ファイルパス>:<行番号>`

**変更の目的**:
<なぜリファクタするか>

**Before**:
```apex
<現在のコード>
```

**After**:
```apex
<リファクタ後のコード>
```

**影響範囲**:
- 呼び出し元への影響: <あり / なし、ありの場合は具体的に>
- テストへの影響: <あり / なし>
- マイグレーション: <データ変更が必要か>

**推奨度**: 高 / 中 / 低
```

### Step 4: リファクタの実施順序を提案

複数のリファクタがある場合、以下の優先順位で提案してください。

```
[優先順位 1: 致命的な問題（バグの原因）]
- ガバナ制限違反の解消
- セキュリティ脆弱性の修正
- 例外処理の追加

[優先順位 2: 構造的な改善]
- 責務分離
- メソッドの分割
- バルク化対応

[優先順位 3: 可読性・保守性]
- 命名改善
- 定数化
- コメント追加
```

### Step 5: 自動適用の提案

ユーザーに以下を確認してください：

```
このリファクタを実際にファイルに適用しますか？

選択肢:
1. すべて一括で適用
2. 高優先度のもののみ適用
3. 1つずつ確認しながら適用
4. 適用しない（提案だけ確認）
```

### Step 6: 適用時の動作

ユーザーが適用を選択した場合：

1. 対象ファイルを実際に編集する
2. 各変更について、変更前後の差分を表示
3. 必要に応じてテストクラスも更新

## 注意事項

### リファクタの原則

```
✓ 一度に1つの問題を修正
✓ 動作を変えずに構造を変える
✓ テストを先に確認（or 追加）
✓ 段階的に進める
✓ 各段階でコンパイル可能な状態を維持
```

### CLAUDE.md の規約を遵守

- バルク化を徹底
- WITH SECURITY_ENFORCED 必須
- 命名規則の準拠
- LeadConstants の使用

### 研修教材としての配慮

- 受講者の学習を促す説明を含める
- 「なぜそうリファクタするか」を必ず説明
- 一度に多くを変えすぎない（学習効果を考慮）
- 必要なら、リファクタの選択肢を複数提示

`force-app/main/default/classes/LeadController.cls`

| 優先度 | カテゴリ | 件数 |

| 高 | ガバナ制限 | 2 |
| 高 | セキュリティ | 3 |
| 中 | 設計 | 1 |
| 中 | 命名 | 2 |
| 低 | コメント | 1 |
| **合計** | | **9** |

---

## 高優先度のリファクタ

### [リファクタ 1] ループ内 SOQL の解消

**カテゴリ**: ガバナ制限
...

---

## 推奨実施順序
1. リファクタ 1, 2 を先に実施（ガバナ制限）
2. リファクタ 3-5 を実施（セキュリティ）
3. テストを実行して動作確認
4. リファクタ 6-7 を実施（設計）
5. 命名・コメントを整理

## 次のアクション

リファクタを実施するか確認:
1. すべて一括で適用
2. 高優先度のみ適用
3. 1つずつ確認しながら適用
4. 適用しない（提案だけ確認）
```

このように動作してください。
